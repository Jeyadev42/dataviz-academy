# Snowflake Query Profiling

Every SQL query in Snowflake generates a **Query Profile** — a visual execution plan showing exactly how your query was processed. Learning to read it is the single most valuable skill for Snowflake performance tuning.

## Accessing the Query Profile

```sql
-- Run your query
SELECT
    c.region,
    p.category,
    SUM(s.quantity * s.unit_price) AS total_revenue,
    COUNT(DISTINCT s.customer_id) AS unique_customers
FROM sales s
JOIN customers c ON s.customer_id = c.customer_id
JOIN products p ON s.product_id = p.product_id
WHERE s.sale_date >= '2025-01-01'
GROUP BY c.region, p.category
ORDER BY total_revenue DESC;
```

After running, click the **Query ID** link in the Results panel → **Query Profile** tab.

## Anatomy of a Query Profile

The profile displays a **DAG of operator nodes**. Each node represents one step in execution:

| Operator | What It Does | Watch For |
|----------|-------------|-----------|
| **TableScan** | Reads data from a table | High bytes scanned = missing pruning |
| **Filter** | Applies WHERE conditions | Should appear early (pushed down) |
| **JoinFilter** | Hash join or merge join | Large build-side = memory pressure |
| **Aggregate** | GROUP BY / window functions | High cardinality = slow aggregation |
| **Sort** | ORDER BY | Spilling to disk = needs bigger warehouse |
| **Result** | Final output | Rows returned vs. rows processed |

## Key Metrics to Check

### 1. Partition Pruning

```
Partitions scanned: 12 out of 1,024 (98.8% pruning)
```

If pruning is low, add a cluster key on your most-filtered column:

```sql
ALTER TABLE sales CLUSTER BY (sale_date);
```

### 2. Bytes Spilled to Local/Remote Storage

Spilling means the warehouse ran out of memory:

- **Spilled to Local** → Manageable, but slows the query
- **Spilled to Remote** → Severe — consider sizing up the warehouse

```sql
-- Check for spilling in recent queries
SELECT query_id, bytes_spilled_to_local_storage, bytes_spilled_to_remote_storage
FROM TABLE(information_schema.query_history())
WHERE bytes_spilled_to_remote_storage > 0
ORDER BY start_time DESC
LIMIT 20;
```

### 3. Exploding Joins

A join that produces more rows than either input table is an **exploding join** — often caused by missing or incorrect join keys.

```sql
-- Before: accidental cross join on non-unique key
SELECT * FROM orders o JOIN order_items oi ON o.order_date = oi.order_date;
-- This joins EVERY order to EVERY item on the same date!

-- After: correct join on unique key
SELECT * FROM orders o JOIN order_items oi ON o.order_id = oi.order_id;
```

## Optimization Checklist

1. ✅ **Prune partitions**: Filter on clustered columns
2. ✅ **Avoid SELECT ***: Only select columns you need
3. ✅ **Push filters early**: WHERE clauses before JOINs
4. ✅ **Check join keys**: Ensure they're unique on at least one side
5. ✅ **Right-size warehouses**: Match warehouse size to query complexity
6. ✅ **Use result caching**: Identical queries within 24h are free
